# Post-mortem: planned storage-server maintenance, SP test target t0143103, 2026-10-12 to 2026-10-16

**Status:** Resolved · **Published:** 2026-11-02 · Live status entry: <https://status.reiers.io>

## Impact

- **Window:** 2026-10-12 06:30 UTC to 2026-10-16 19:15 UTC. The collector recorded t0143103 as not `ok` for 1,285 consecutive probes, about 107 hours.
- **Proving:** WindowPoSt failed while the sealed sectors were unreachable, and sectors were marked faulty. All sectors recovered after storage was restored. Confirmed 2026-11-02: 1,285 live, 1,285 active, 0 faulty.
- **Faucet and Calix:** not affected.
- **Availability:** the window is counted as downtime because the maintenance notice went up during the window (2026-10-14) rather than 24 hours before it (SLO.md §2.2). October SP availability: 84.91%; 99.44% outside the window.
- **Data:** no sectors lost. All 1,285 recovered.

## Timeline (UTC)

- 2026-10-12 ~06:30: the storage server backing t0143103's sealed sectors goes into planned maintenance. Calix stops seeing blocks from t0143103; the collector starts recording failures.
- 2026-10-12 to 2026-10-14: WindowPoSt fails on every deadline that touches the sealed sectors.
- 2026-10-14 ~17:10: status page and Calix switch the SP from "outage" to a maintenance notice with an expected return time.
- 2026-10-15: the storage server is back, but its export path has changed. The mount on the proving node is remounted at the new path.
- 2026-10-16 morning: Curio still cannot reach the sectors. Its storage configuration lists two paths inside a single entry, so only the second (now wrong) path is read. The configuration is rewritten with one entry per path, Curio is restarted, and the storage path is attached explicitly.
- 2026-10-16 ~19:15: t0143103 producing blocks again; the collector records `ok`. All sectors reported recovered that evening. Status page set back to Operational.

## Root cause

The storage server holding the sealed sectors was taken down for planned maintenance. Three things made the SP outage longer than the maintenance itself:

1. The storage server came back with a different export path, so the existing mount no longer pointed at the data.
2. Curio's storage configuration had a malformed entry (two `Path` keys in one object). Only one path was being read, and after the path change it was the wrong one.
3. Curio did not re-register the storage path on restart; it had to be attached by hand.

## What we are changing

- SP maintenance is now announced at least 24 hours ahead on the status page and in `#fil-net-calibration-discuss`, with storage paths recorded beforehand so the post-maintenance check is quick.
- A block-production alert for t0143103 (open since the October 1 follow-ups) is scheduled for November.
